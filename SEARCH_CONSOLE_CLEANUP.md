# Google Search Console cleanup — legacy WordPress spam artifacts

## What was found

The Search Console data pulled into the automated SEO reports (`reports/seo/`) shows this domain previously ran WordPress and appears to have been hit by a spam-injection compromise before the current site was built. Evidence, all visible in `reports/seo/latest.md` and the dated `data-*.json` files:

- **Two spam sitemaps still registered and being crawled:**
  - `https://barakaevents.com/wp-links-opmll.php?s=s&t=1&m=3&cn=37`
  - `https://barakaevents.com/index.php?r=s&t=1&m=3&cn=32`
  - Neither is a real WordPress core file or a page that exists on the current site. `wp-links-opmll.php` in particular is a classic filename pattern used by WordPress malware droppers to serve injected spam sitemaps.
- **Indexed spam/legacy pages** that don't exist on the current React site: `/birthday-planners/`, `/corporate-event-planner/`, `/wedding-planner/`, and URLs with tracking-style query params like `?JGNS=NOU277933373&g=&m=3`.
- **Spam search queries** the domain is (barely) ranking for: *"bf picture janwar wali"*, *"janwar wala bf picture"*, *"janwar wali bf picture"* — foreign-language spam-injection query patterns, not anything related to Baraka Events.

The only legitimate sitemap already registered is `https://barakaevents.com/sitemap.xml` — that one is correct and current, generated by this repo.

## Why this matters

Google associates all of this with the domain's trust signals. Leftover spam sitemaps and indexed spam pages can suppress how much Google trusts and ranks the domain overall, independent of how good the current site is. This won't fix itself — it needs to be manually removed from Search Console.

## Steps to fix

1. **Sign in to [Google Search Console](https://search.google.com/search-console)** for the `barakaevents.com` / `www.barakaevents.com` property.

2. **Remove the two spam sitemaps:**
   - Go to **Sitemaps** in the left sidebar.
   - Find `wp-links-opmll.php?s=s&t=1&m=3&cn=37` and `index.php?r=s&t=1&m=3&cn=32` in the submitted sitemaps list.
   - Click the **⋮** menu next to each → **Remove sitemap**.
   - Leave `sitemap.xml` in place — that's the real one.

3. **Request removal of the spam pages** (temporary, ~6 months, but stops them showing in search immediately):
   - Go to **Removals** → **New Request**.
   - Submit each spam URL found in the reports (`/birthday-planners/`, `/corporate-event-planner/`, `/wedding-planner/`, and any `?JGNS=...` URLs you see under **Pages** → **Not indexed** or in search results).
   - Note: this repo's routing (`vercel.json`) sends every unmatched path to `index.html` with an HTTP 200, so these spam URLs currently return a *soft 404* (the page loads and shows the app's own "not found" view, but the server status is 200, not a real 404). Google treats soft 404s less decisively than a real 404/410, so the Removals tool above is the actual fix here — it works regardless of status code. A code-level fix (making Vercel return a true 404/410 for these specific dead paths) is possible but touches the site's core routing config, so it's worth doing separately and carefully rather than as part of this cleanup.

4. **Check for a manual action or security issue:**
   - Go to **Security & Manual Actions** → **Manual actions** and **Security issues** in the sidebar.
   - If either shows anything, that confirms Google flagged the compromise directly — follow Google's specific instructions there and file a **reconsideration request** once resolved.

5. **Re-verify ownership** if you haven't already confirmed you (not a previous owner/developer) hold sole access to this Search Console property, since a leftover compromise sometimes means old, unknown parties still have property access.

6. **Monitor**: the next few automated daily SEO reports (`reports/seo/latest.md`) will show whether the spam queries/pages/sitemaps disappear from the data. If the two spam sitemaps still show up in a report a week or two after removal, they were likely resubmitted by something still active on the server — worth a deeper look at DNS/hosting history for anything else pointing at this domain.

## What does *not* need fixing here

The current site (this repo) is clean — it only generates and submits the one legitimate `sitemap.xml`, and nothing in the codebase references or serves any of the spam paths above. This is purely a Search Console configuration cleanup, not a code issue.
